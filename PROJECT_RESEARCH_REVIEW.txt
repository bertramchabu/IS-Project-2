NETVISION AI - PROJECT AND RESEARCH REVIEW
Review date: 30 October 2026
Repository: IS-Project-2
Purpose: Review the application, model pipeline, project proposal and recent
research; recommend practical improvements and proposal changes.

EXECUTIVE SUMMARY
-----------------
NetVision AI has a useful end-to-end prototype: a Flutter dashboard, Firebase
authentication and Firestore repositories, callable model inference, a
BiLSTM/TensorFlow Lite deployment path, telemetry replay/simulation, and tests.
The model service validates authenticated requests and finite KPI values.

The main priority is not replacing the BiLSTM. It is establishing that the
reported results measure what the proposal claims. The current training data
is generated by the project's own fault simulator; the classifier is trained
on a hand-designed continuous fault-probability curve; validation uses
overlapping windows; and the comparative script hard-codes detection latency
and SUS scores. The stored comparison also reports a higher F1 for the
threshold baseline (0.9308) than for the BiLSTM (0.8593). These results do not
currently demonstrate that the model improves F1 or detection time on real
network conditions.

Recommendation: keep the BiLSTM as the current prototype, make the evaluation
reproducible and appropriately cautious, then use recent papers to guide
controlled baseline/model comparisons. Update the proposal after supervisor
approval so that it describes the built system and a defensible evaluation.
This review did not edit "IS project.txt".

PROJECT STRENGTHS
-----------------
1. The Flutter code is separated into repositories, BLoCs, models and views;
   model inference is routed through an authenticated Firebase callable.
2. The callable requires Firebase authentication, checks the ten-step/five-KPI
   input shape and rejects non-finite KPI values.
3. Training and evaluation scripts, generated CSVs, model artifacts, plots,
   metadata and unit/widget tests are present.
4. The dashboard can continue displaying telemetry when inference is
   unavailable, rather than silently presenting a fabricated model result.
5. The proposal states meaningful performance, usability and adaptive
   monitoring goals. The implementation is substantial enough to support a
   useful prototype evaluation once its claims and methods are aligned.

HIGH-PRIORITY FINDINGS
----------------------

P0 - Check and replace the Firestore rules before any public deployment.
firestore.rules permits unauthenticated reads and writes to every document
until 3 November 2026, after which access is denied by default. This is the
repository rule file; this review did not verify whether those exact rules are
currently deployed. Replace the blanket rule with collection-specific
authentication, role/ownership checks and least-privilege writes, then test
the rules in the Firebase Emulator and verify the deployed rules. Do not treat
Firebase Authentication in the app as a substitute for Firestore rules.

P1 - Replace the comparison's assumed values with measured results.
model/src/baseline_comparator.py sets baseline detection latency to 31.4
seconds, BiLSTM detection latency to 1.25 seconds, and SUS scores to 54.2 and
83.5 in code. These are not measurements produced by that script. Do not
present the speedup, usability scores, or alert-fatigue reduction as observed
findings unless raw timing records and the actual SUS questionnaires support
them. Keep SUS results separate from model metrics.

P1 - Correct the F1 comparison and align the baseline evaluation.
model/results/comparative_evaluation.json records baseline F1=0.9308 and
BiLSTM F1=0.8593, so the reported comparison does not show an F1 improvement.
The proposal's baseline target of 0.50 is not a measured result. The comparator
also evaluates raw rows for the baseline but window endpoints for the model.
Evaluate both methods on the same held-out timestamps, fault labels, forecast
horizon and alert rules. Recompute all metrics from those aligned predictions.
The comparator's "false_alert_rate" is FP/(FP+TP), the fraction of triggered
alerts that are false, not the conventional false-positive rate FP/(FP+TN).
Name this measure accurately or report both quantities.

P1 - Make validation representative and prevent boundary leakage.
model/src/train.py uses Keras validation_split on concatenated, per-node
stride-one windows. Keras selects the final 15% before shuffling training
examples; because windows are grouped by node, this validation set can be
dominated by the final node's time tail rather than representing all nodes.
The windows immediately across the train/validation boundary also share
nine of ten timesteps. Use explicit chronological, blocked partitions per
node (or held-out nodes/sites where feasible), with a gap at least as large
as the input window at split boundaries. Select the alert threshold on
validation data only, lock it, and report test results once. Preserve the
final test set from tuning.

P1 - Be precise about the probability target and RMSE.
model/src/dataset_generator.py constructs fault_probability_target from
hand-authored precursor/fault/recovery ramps. model/src/train.py trains the
sigmoid output against that continuous curve, while F1 is calculated using
fault_label and a separate classification threshold. The reported RMSE
therefore measures fit to the simulator's designed curve, not calibrated
real-world fault probability. Explain this target accurately; consider naming
it a synthetic risk/precursor score. For probability calibration, evaluate
against independently defined binary outcomes using Brier score and a
reliability/calibration plot, in addition to classification metrics.

P1 - Separate synthetic feasibility from real-network effectiveness.
The checked-in generator creates the labels and KPI patterns from scripted
fault scenarios; train and test originate from that generator and four
simulated nodes. This is useful for a prototype, but it does not establish
generalization to real network devices or operators. Add a clearly scoped
limitation. If access allows, evaluate on a separate testbed or appropriately
anonymized real telemetry; otherwise describe the results as synthetic-data
results only.

P2 - Report event-level operational outcomes, not only window scores.
Overlapping one-second windows make sample counts look larger than the number
of independent fault episodes. In addition to F1/precision/recall, report
fault-event recall, missed events, false alarms per node-hour/day, lead time
before the defined event onset, alert delay, and confidence intervals
clustered by event or node. State the event definition and forecast horizon.
The proposal's two-second detection target and the report's 1.25-second
anticipation claim are different measurements and must not be conflated.

P2 - Make the threshold and savings claims match deployed behavior.
The proposal/deployment use a 0.70 alert threshold, but evaluation uses 0.65.
Choose and justify one threshold using validation data, or describe the
difference explicitly. The deployed callable returns a ten-second next
inference interval for low risk, while the Flutter client enforces the delay.
This reduces inference calls under the expected schedule; it does not by
itself reduce KPI collection, Firestore writes, chart refreshes, or total
system cost by 90 percent. Measure and name the specific resource saved.

P2 - Align the proposal with the actual architecture and scope.
The proposal refers in different places to REST/WebSocket, TFLite or ONNX,
SQL tables, and Cloud Functions that write KPI records. The README and code
describe Firestore telemetry plus authenticated Firebase callable inference
using TFLite; FastAPI is an optional local service. Describe the path actually
used for the final demonstration. Use Firestore collections/documents rather
than relational-table language where describing implementation. Reconcile
three KPI charts in Objective I with the implementation/README's five KPI
charts, and the proposal's three objectives in the abstract with its four
specific objectives.

P2 - Treat the local FastAPI service as a separate development surface.
model/api/app.py configures wildcard CORS with credentials and its routes do
not show authentication; it stores live buffers in process memory. Keep it
bound to localhost for local use, or add explicit authentication, restrictive
CORS, bounded/expiring per-node state and deployment hardening before exposing
it. This is separate from the authenticated Firebase callable path.

P3 - Verify user-study evidence and bibliography details.
The repository stores SUS values but this review did not find participant
responses or calculation records in the examined evaluation artifacts.
Retain the questionnaire responses, scoring worksheet, participant count and
consent/ethics documentation; report a small purposive sample as exploratory.
Verify every proposal citation against its publisher/DOI record. Several
references in the current bibliography lack complete journal/volume/DOI
details or have malformed author/title text. Also check publication dates
against the proposal's stated May 2026 date and cite the version actually
consulted.

RECENT RESEARCH AND PRACTICAL RELEVANCE
---------------------------------------
The following papers are recent and relevant; DOI links point to publisher or
preprint records. Research relevance is not evidence that a different model
will outperform this project's model.

1. Seliem, M., Roedig, U., Sreenan, C. J., & Pesch, D. (2025).
   "BiLSTM-Based Fault Anticipation for Predictive Activation of FRER in
   Time-Sensitive Industrial Networks." IoT, 6(4), article 60.
   https://doi.org/10.3390/iot6040060
   Directly related to KPI-based BiLSTM anticipation in time-sensitive
   industrial networking and reducing always-on redundancy overhead. It is
   useful related work for the proposal, but its network domain and system
   objective differ from NetVision AI; do not transfer its results as if they
   were NetVision measurements.

2. Qiu, X., Li, Z., Qiu, W., Hu, S., Zhou, L., Wu, X., Li, Z., Guo, C.,
   Zhou, A., Sheng, Z., Hu, J., Jensen, C. S., & Yang, B. (2025).
   "TAB: Unified Benchmarking of Time Series Anomaly Detection Methods."
   Proceedings of the VLDB Endowment, 18(9), 2775-2789.
   https://doi.org/10.14778/3746405.3746407
   TAB describes a unified evaluation over 29 multivariate datasets and
   multiple method families, emphasizing dataset and protocol choices. The
   actionable lesson is to publish a reproducible, apples-to-apples evaluation
   protocol and compare against credible simple and learned baselines.

3. He, S., He, W., Du, M., Jiang, X., & Dong, Y. (online publication listed
   2025; verify final issue year in the publisher record).
   "GDCMAD: Graph-based dual-contrastive representation learning for
   multivariate time series anomaly detection." Information Sciences.
   https://doi.org/10.1016/j.ins.2025.122790
   This is relevant to modeling cross-variable relationships. It motivates
   testing graph-aware methods only if the project represents meaningful
   relationships among KPIs or network nodes; it is not a reason to add a
   graph model to the current single-node, five-feature pipeline without data
   and a controlled comparison.

4. Lee, J., Lee, J., & Kim, S. B. (2025).
   "Uncertainty-informed dynamic threshold for time series anomaly detection."
   Expert Systems with Applications, 278, article 127379.
   https://doi.org/10.1016/j.eswa.2025.127379
   This work is a useful source when discussing threshold selection and
   uncertainty. A sensible project extension is to compare a fixed,
   validation-selected 0.70 operating threshold with a calibrated or
   uncertainty-aware alternative, using the same validation/test protocol and
   reporting false alarms and missed events. Do not claim adaptive thresholds
   are safer until tested.

RECOMMENDED ACTION PLAN
-----------------------
1. Immediately verify whether permissive Firestore rules are deployed; replace
   and test them before the 3 November 2026 rule expiry or any public demo.
2. Freeze the current artifacts and record their hashes/versions. Avoid
   running the training pipeline without a backup because it regenerates the
   datasets, scaler and model files.
3. Repair the evaluation protocol: deterministic chronological partitions,
   blocked validation, consistent threshold, aligned baseline timestamps,
   measured end-to-end latency and real SUS records.
4. Re-run the evaluator and comparator from raw prediction outputs; regenerate
   JSON/plots and correct README/status/proposal claims to match.
5. Test the exported TFLite model against the Keras model on the same fixed
   examples and report both warm and cold end-to-end latency, not just one
   single inference.
6. Only after the evaluation is sound, benchmark one or two relevant
   alternatives (for example a simple threshold/linear baseline and a compact
   temporal CNN/GRU; consider graph-aware methods only if suitable topology
   data exists).
7. Obtain supervisor approval, then update the formal proposal using the
   documented implementation and verified sources.

RECOMMENDED CHANGES TO "IS project.txt"
---------------------------------------
Yes, changes are recommended. The safest course is to keep the current file
unchanged until the supervisor approves substantive research-method changes.
The following edits are concrete and traceable:

- Abstract/background/literature review: add the verified 2025 papers above
  where relevant; verify and complete every existing citation. State that the
  current model is evaluated on generated data unless separate real data are
  collected.
- Objectives: make the dashboard KPI count consistent; state the actual
  inference deployment path; distinguish binary classification, probability
  calibration and detection/anticipation timing.
- Methodology: specify dataset origin, generator/seed, node/time partitions,
  window size, validation-only threshold selection, aligned baselines,
  event-level metrics, latency measurement procedure and SUS data handling.
  Remove assumed baseline scores and assumed SUS values as targets presented
  as observations.
- System analysis/design: align descriptions/diagrams to Firestore and the
  Firebase callable/TFLite implementation. Keep the optional FastAPI path
  clearly separate. State the access-control rules and role policy.
- Results/discussion (when available): report actual recomputed values,
  confusion matrices, test-set definition, confidence intervals and study
  sample size. Explicitly discuss baseline F1 being higher if that remains true.
- Limitations: identify synthetic data, small/limited usability sample, and
  the gap between inference throttling and total telemetry/cloud-cost savings.

Suggested wording for the proposal's evaluation limitation:
"The initial model evaluation uses simulated multivariate KPI sequences with
scripted fault patterns. Results therefore measure performance on the stated
simulation and do not establish generalization to operational networks.
Where real testbed or operational telemetry is unavailable, conclusions will
be limited to prototype feasibility. Thresholds will be selected on a
validation partition and evaluated once on a temporally separate test
partition; comparative methods will be evaluated on the same timestamps and
fault definitions."

Suggested reporting caveat until the results are regenerated:
"Repository evaluation files currently record a BiLSTM F1-score of 0.8593 and
a threshold-baseline F1-score of 0.9308. These stored values have not been
independently reproduced in this review, and the code contains assumed
detection-latency and SUS values. The comparison should not be presented as
evidence of improved F1, measured speedup or observed usability until the
evaluation is corrected and rerun."
